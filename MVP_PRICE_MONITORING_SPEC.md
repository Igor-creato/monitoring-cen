# MVP Specification: Price Monitoring by Product URL

## 1. Цель продукта

MVP сервиса мониторинга цены по ссылке на товар для рынка Россия/СНГ.

Пользователь вставляет URL товара, задает целевую цену, а сервис периодически проверяет текущую цену и отправляет уведомление, когда цена становится меньше или равна целевой.

Главная гипотеза MVP: пользователям достаточно ручного добавления конкретных ссылок без поиска, сравнения и склейки товаров между магазинами.

Ключевое ограничение MVP: сервис не должен пытаться парсить весь интернет. Поддерживаются только заранее разрешенные домены через отдельные parser adapters.

## 2. Что входит в MVP

- Регистрация и авторизация пользователя.
- Добавление одной ссылки на товар.
- Первичная проверка ссылки перед созданием мониторинга.
- Указание целевой цены.
- Периодическая проверка цены.
- История успешных и неуспешных проверок.
- Статус задачи мониторинга.
- Лог ошибок парсинга.
- Email-уведомления.
- Telegram-уведомления как опциональный канал.
- Архитектурная возможность позже добавить push/SMS.
- Ограниченный whitelist поддерживаемых доменов.
- Docker Compose окружение:
  - FastAPI API service
  - PostgreSQL или MariaDB
  - Redis
  - scheduler
  - parser worker
  - notification worker

## 3. Что не входит в MVP

- Поиск товара по названию.
- Склейка одинаковых товаров между маркетплейсами.
- Сравнение по нескольким ссылкам в одном действии.
- Мобильное приложение.
- Корзины.
- Сложная аналитика.
- Прогнозы цен.
- Рекомендации товаров.
- Расширение браузера.
- Учет кэшбэка, промокодов, баллов, бонусов и доставки.
- Авторизация на сайтах магазинов от имени пользователя.
- Мониторинг страниц, доступных только после логина.
- Массовый импорт ссылок.
- Выбор региона пользователя.

## 4. Пользовательские сценарии

### Создание мониторинга

1. Пользователь регистрируется или входит.
2. Вставляет ссылку на товар.
3. Сервис проверяет URL:
   - схема только `http` или `https`;
   - домен есть в whitelist;
   - URL не ведет на localhost/private network;
   - URL можно нормализовать.
4. Сервис выполняет первичный парсинг.
5. Если цена найдена, пользователь задает целевую цену.
6. Пользователь выбирает канал уведомления:
   - email;
   - Telegram, если подключен.
7. Создается задача мониторинга со статусом `active`.

### Периодическая проверка цены

1. Scheduler выбирает активные задачи, которые пора проверить.
2. Parser worker загружает страницу и запускает adapter для домена.
3. Результат сохраняется в историю проверок.
4. Если `current_price <= target_price`, создается событие уведомления.
5. Notification worker отправляет уведомление.
6. После успешной отправки задача переводится в `triggered`.

MVP-правило: после первого успешного уведомления задача больше не проверяется автоматически, пока пользователь не активирует ее заново.

### Просмотр мониторинга

Пользователь видит:

- товар;
- ссылку;
- текущую цену;
- целевую цену;
- валюту;
- статус;
- дату последней проверки;
- дату последнего успешного парсинга;
- историю проверок;
- последние ошибки.

### Изменение целевой цены

1. Пользователь открывает задачу.
2. Меняет целевую цену.
3. Если задача была `triggered`, ее можно вернуть в `active`.

### Остановка мониторинга

Пользователь может поставить задачу на паузу или удалить ее. Удаление в MVP должно быть soft delete.

## 6. Бизнес-правила

- Один мониторинг = одна ссылка = одна целевая цена.
- Один пользователь не может иметь две активные задачи на один `normalized_url`.
- Цена сравнивается по правилу `current_price <= target_price`.
- Валюта не конвертируется.
- Если валюта изменилась, цену не сравнивать и записать ошибку `currency_changed`.
- Первичный парсинг обязателен перед созданием активной задачи.
- Если цена не найдена при первичном парсинге, активная задача не создается.
- Проверка цены выполняется асинхронно worker-процессом, не внутри API request lifecycle.
- После успешного уведомления задача получает статус `triggered`.
- Повторные уведомления по одной и той же задаче не отправляются, пока пользователь не активирует задачу заново.
- После 5 подряд ошибок задача переводится в `error`.
- Минимальный интервал проверки одной задачи: 6 часов.
- Лимит активных задач на пользователя для MVP: 20.
- В MVP цена считается без доставки, промокодов, баллов, бонусов, кэшбэка и персональных скидок.
- В MVP используется один системный регион по умолчанию, например Москва.

## 7. Статусы мониторинга

- `draft` - задача создана, но первичная проверка еще не завершена.
- `active` - задача активна и проверяется по расписанию.
- `paused` - пользователь вручную остановил мониторинг.
- `triggered` - цена достигла порога, уведомление отправлено.
- `error` - задача остановлена из-за повторяющихся ошибок.
- `unsupported` - домен или формат страницы не поддерживается.
- `deleted` - задача мягко удалена.

## 8. Ошибки и edge cases

### Неподдерживаемый домен

- Не создавать активную задачу.
- Вернуть понятную ошибку.
- Логировать домен для анализа спроса.

### URL не является карточкой товара

- Первичный парсинг не проходит.
- Задача не создается как `active`.

### Цена отсутствует

Возможные причины:

- товар закончился;
- страница изменилась;
- требуется выбор варианта;
- требуется авторизация;
- регион не выбран;
- сайт изменил верстку.

MVP-решение: записать ошибку парсинга и не отправлять уведомление.

### Капча или антибот

- Записать `captcha_detected`.
- Использовать retry/backoff.
- После 5 подряд ошибок перевести задачу в `error`.

### Редиректы

- Сохранять исходный URL и `normalized_url`.
- Если редирект ведет на поддерживаемый домен, использовать итоговый URL как `normalized_url`.
- Если редирект ведет на неподдерживаемый домен, не создавать активную задачу.

### Подозрительная цена

- Цена `0` не должна вызывать уведомление.
- Слишком низкая цена должна помечаться как `suspicious_price`.
- Для MVP можно использовать простое правило: не уведомлять, если цена меньше 1 рубля.

### Товар удален

- При 404 записывать ошибку.
- После 5 подряд 404 перевести задачу в `error`.

### Региональные цены

Спорное место: цены в РФ часто зависят от города.

MVP-ограничение: один системный регион, без выбора региона пользователем.

### Цена с картой магазина, бонусами и купонами

Спорное место: пользователь может ожидать "финальную" цену.

MVP-ограничение: сравнивать только публичную цену на странице без авторизации и дополнительных условий.

## 9. Нефункциональные требования

### Производительность

- API p95 до 300 мс для CRUD-запросов без парсинга.
- Первичный preview может быть медленнее, но должен иметь timeout.
- Рекомендуемый timeout первичного парсинга: 15 секунд.
- Все периодические проверки выполняются worker-процессами.

### Надежность

- Redis используется для очередей и retry.
- Ошибка одного домена не должна блокировать проверки других доменов.
- Notification sending должен иметь retry.
- Проверки должны быть идемпотентными.

### Масштабируемость

- API, scheduler, parser workers и notification workers должны быть отдельными процессами/сервисами.
- Добавление нового домена должно происходить через новый parser adapter.
- Бизнес-логика мониторинга не должна зависеть от конкретного парсера.

### Наблюдаемость

Логировать для каждой проверки:

- `monitored_item_id`
- `domain`
- `parser_type`
- `duration_ms`
- `status`
- `error_code`
- `http_status`

Метрики:

- количество успешных проверок;
- количество ошибок;
- error rate по доменам;
- количество отправленных уведомлений;
- размер очередей;
- средняя длительность проверки.

### Безопасность

- Разрешены только `http` и `https`.
- Обязательная SSRF-защита:
  - запрет localhost;
  - запрет private IP;
  - запрет link-local адресов;
  - запрет internal hostnames;
  - запрет нестандартных схем.
- Разрешены только домены из whitelist.
- Rate limit на создание задач.
- Не логировать пароли, токены и лишние персональные данные.
- Telegram bot token хранить только в server-side config/env.

### Операционные риски

- Парсинг маркетплейсов может ломаться из-за изменений верстки.
- Парсинг может блокироваться антиботом.
- Должна быть возможность быстро отключить домен через `SupportedDomain.is_enabled`.
- Пользователю нельзя обещать абсолютную точность или гарантированную частоту проверки.

## 10. API endpoints верхнего уровня

### Auth

- `POST /auth/register`
- `POST /auth/login`
- `POST /auth/logout`
- `GET /auth/me`

### Notification channels

- `GET /notification-channels`
- `POST /notification-channels/email`
- `POST /notification-channels/telegram/start`
- `POST /notification-channels/telegram/confirm`
- `PATCH /notification-channels/{id}`
- `DELETE /notification-channels/{id}`

### Monitored items

- `POST /monitored-items/preview`
  - Проверяет ссылку, запускает первичный парсинг, возвращает товар, цену, валюту и домен.

- `POST /monitored-items`
  - Создает мониторинг.

- `GET /monitored-items`
  - Возвращает список мониторингов пользователя.

- `GET /monitored-items/{id}`
  - Возвращает детальную карточку мониторинга.

- `PATCH /monitored-items/{id}`
  - Меняет целевую цену, статус или канал уведомления.

- `DELETE /monitored-items/{id}`
  - Выполняет soft delete.

### Price checks

- `GET /monitored-items/{id}/price-checks`
  - История проверок, цен и ошибок.

### Admin/system

- `GET /admin/supported-domains`
- `POST /admin/supported-domains`
- `PATCH /admin/supported-domains/{id}`
- `GET /admin/parser-health`
- `GET /admin/queues`

Admin endpoints можно закрыть простым internal/admin auth механизмом на MVP.

## Архитектурные указания для code-generation agent

- При реализации обращаться к этому файлу как к источнику продуктовых требований.
- Не добавлять фичи из Backlog v2 в MVP без явного запроса.
- Не реализовывать универсальный парсер всех сайтов.
- Начинать с whitelist доменов и parser adapter interface.
- Все проверки цены выполнять через worker, кроме ручного `preview`.
- Не отправлять повторные уведомления после `triggered`.
- Не сравнивать цены при неизвестной или изменившейся валюте.
- Не учитывать скидки, бонусы, доставку и персональные цены.
- Сначала сделать надежный backend API, очереди, историю проверок и уведомления.
